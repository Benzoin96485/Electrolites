## 1. fp64 除法为什么贵？

### 1.1 一行除法不代表一条廉价机器指令

`fp64` 即 64 位浮点数，通常有 53 位二进制有效精度。GPU 上的加法、乘法和融合乘加（FMA，计算 `a*b+c` 并只做一次最终舍入）有很高的吞吐率。除法需要确定一个商，并满足相应的精度、舍入和特殊输入语义，其实现成本通常更高。

例如，近似计算 `1/x` 后乘以分子，只能得到商的近似值。为了得到双精度结果，还可能需要修正近似、处理极大或极小的数以及零、无穷大等情况。编译器可以把源码中的一次除法展开为多条指令。PTX 中出现一条 `div` 也不表示最终硬件执行时只有一条同成本的指令。具体展开取决于 GPU 架构、编译器、编译选项和编译器能证明的输入条件。[NVIDIA PTX 的除法定义](https://docs.nvidia.com/cuda/archive/12.1.1/parallel-thread-execution/index.html#floating-point-instructions-div)

这里还要区分两个概念：**延迟**是一个结果多久才能供后续指令使用；**吞吐率**是机器持续工作时单位时间能完成多少次运算。如果循环下一步必须等待除法结果，就会遇到依赖链的延迟；即使有很多独立任务，除法相关指令也会消耗执行资源。仓库记录的某次编译中除法展开的指令数量，是该环境的观察，不应写成“所有 GPU 的 fp64 除法固定需要若干条指令”。

### 1.2 首先减少次数，再考虑改变算法

假设内层循环反复计算

```text
u = a / p
v = b / p
w = c / p
```

且 `p` 在循环内不变，可以先求 `r = 1/p`，再用三个乘法。对于同一个 bra primitive pair，指数和等分母会被许多 ket 组合复用，这正是提取循环不变量的机会。

不过，`a/p` 与 `a*(1/p)` 在浮点数上不保证逐比特相同；倒数还可能遇到与原除法不同的上溢、下溢情形。这里能否使用，取决于积分算法的输入范围和数值验证，不能推广成对任意程序机械替换所有 `/`。

VV10 的双重网格求和中，还有另一种方法：先取得便宜的倒数近似，再进行 Newton 修正。若目标为 $1/x$，迭代是

$$
r_{n+1}=r_n(2-xr_n).
$$

设 $r_n=(1-e_n)/x$，在精确算术下就有 $e_{n+1}=e_n^2$。因此初始近似已经不错时，少量迭代能迅速提高精度。实际浮点计算还受舍入影响；这解释了算法为何有效，但不是全输入范围的正确舍入证明。

`fastnlc` 的快速倒数路线必须与远场混合精度、网格裁剪分开评价：它们改变的是不同环节。`FASTNLC_MODE=fp64` 并不自动禁用快速倒数；源码还提供 `FASTNLC_RCP` 控制项。参见[实现](../../electrolites/fastnlc.py)与[已有测量](../README_fastnlc.md)。

## 2. 为什么统一称为“共享内存”？

一个线程通常把少量正在使用的数放在寄存器中；一个线程块内的线程可以通过**共享内存**共同访问数据；更大的数组通常在 GPU 显存中。L1/L2 缓存又是另一层概念，它们由硬件参与管理。

共享内存的“共享”范围通常是一个线程块，并不意味着整张 GPU 上所有线程都能直接读同一个共享数组。程序员安排哪些线程写入数据，其他线程何时读取，并在需要时同步。这样做可以避免相同数据被反复计算或从显存重复读取。

例如，一个线程块将若干 bra primitive pair 的指数和、乘积中心写入共享内存；之后不同线程处理不同 ket pair 时读取这些值。应称为“bra 数据在共享内存中复用”，而不是让读者猜测“共享缓存”究竟指 CUDA shared memory、L2，还是 Python 字典。

共享内存也有成本：占得太多，会减少同一 SM 上同时驻留的线程块数量；还可能需要同步，或者出现多个线程访问映射到同一存储 bank 所导致的冲突。寄存器、共享内存和并行度之间需要共同取舍。

## 3. “只由 bra primitive pair 决定”究竟是哪几个量？

### 3.1 先区分壳层与 primitive

一个收缩高斯基函数由多个 primitive Gaussian 按系数组合。四中心积分写作 $(ij|kl)$ 时，通常把前两个函数称为 bra，后两个称为 ket。**固定壳层对**不等于固定 primitive pair：如果壳层 $i,j$ 各有 6 个 primitive，就有 36 个指数与系数组合。

先看不含角动量多项式的两个高斯因子：

$$
e^{-a|\mathbf r-\mathbf A|^2}e^{-b|\mathbf r-\mathbf B|^2}
=e^{-\frac{ab}{p}|\mathbf A-\mathbf B|^2}
 e^{-p|\mathbf r-\mathbf P|^2},
\qquad p=a+b,\quad
\mathbf P=\frac{a\mathbf A+b\mathbf B}{a+b}.
$$

这就是高斯乘积定理：两个高斯相乘，得到一个以 $\mathbf P$ 为中心的高斯，再乘一个与电子坐标无关的系数。多项式部分可以另外展开，不会改变这个指数因子的乘积中心。

例如一维的 $A=0,B=2,a=3,b=1$，有 $P=0.5$。中心更靠近指数较大、分布较窄的那个高斯。换成另一个 ket pair，并不会改变这里的 $p$ 或 $P$。

### 3.2 可以复用什么，不能复用什么？

对固定的 bra primitive pair，下列量固定：

- 指数和 $p=a+b$ 及其倒数；
- 乘积中心 $\mathbf P$，以及 $\mathbf P-\mathbf A$、$\mathbf P-\mathbf B$；
- 高斯衰减因子 $\exp[-ab|\mathbf A-\mathbf B|^2/p]$；
- 该 primitive pair 的收缩系数乘积，以及需要时的 $2a,2b$。

令 ket 的指数和与乘积中心为 $q=c+d$、$\mathbf Q$，则

$$
T=\frac{pq}{p+q}|\mathbf P-\mathbf Q|^2
$$

同时依赖 bra 和 ket，不能只用 bra 预先算好。$1/(p+q)$ 也一样。

因此优化后的组织是“每个 bra primitive pair 先算一次自己的数据，再与许多 ket pair 组合”，不是“同一壳层对的所有 primitive 共用一个中心”。共享内存中的数组仍然需要 primitive-pair 下标。收缩深度增加时，数组容量也要增加；这解释了为什么容量取决于基组，而不只是原子数。[K 实现](../../electrolites/fastk.py)、[K 内核公共代码](../../electrolites/kernels/fastk_prologue.cu)、[primitive-pair 容量说明](../PRIM_PAIR_AND_JIT.md)

## 4. 怎样判断“一线程处理一个 quartet”是否合适？

这里说的 quartet 是一次壳层四元组任务；它内部仍包含 primitive 组合和角动量分量。一线程一个任务，意味着由该线程推进这些循环并保留自己的中间结果，不意味着只做一次浮点乘法。

它的好处是线程之间少交换中间量，也可能减少共享内存和同步。是否划算，首先取决于**一个任务需要同时保留多少数据**，其次是有多少独立任务可并行，以及任务耗时是否均衡。

Cartesian 角动量为 $l$ 的壳层有 $(l+1)(l+2)/2$ 个函数。因此，`ssss` 只有 1 个 AO 积分分量，`pppp` 有 $3^4=81$ 个，`ffff` 有 $10^4=10000$ 个。假如一次把 81 个双精度结果都保留在寄存器中，仅这些值就可能需要约 162 个 32 位寄存器位置，尚未计算递推和地址等临时量。

这不是说所有 `pppp` 实现都一定占 162 个寄存器：编译器可以缩短变量生命周期，算法也可以分批收缩而不同时保留全部结果。这个估算的作用是提前发现压力，不是代替编译报告。高角动量时，让多个线程分摊分量、用共享内存交换结果，常常更合理。

判断时需要同时看：

| 观察对象 | 为什么重要 |
|---|---|
| 编译后的寄存器数量、local load/store | 数据放不下时可能发生寄存器溢出，增加线程私有 local memory 的访问 |
| 每个 block 的共享内存、实际驻留数 | 较低同步成本可能被较低并行度抵消 |
| primitive 收缩深度 | 增加循环长度与 pair 数据容量，但不必然同比增加所有同时存活的输出 |
| 筛选后 quartet 数与长短任务分布 | 任务太少或少数任务很长，都可能让部分 SM 提前空闲 |
| 单密度/多密度、输出累计成本 | 积分便宜后，读密度和原子累计可能成为主要耗时 |
| 最终矩阵的正确性与总耗时 | 单看某个算术片段快，不足以决定实际内核选择 |

仓库按角动量类配置线程组织，而不是对所有 quartet 统一使用一种布局。最可靠的过程是：建立候选布局 → 检查最终 J/K → 查看寄存器和溢出 → 在代表性体系上计时。单线程和多线程合作只是候选，不是“低角动量必胜”的硬规则。[K 优化说明](../README_fastk.md)、[代码生成器](../../electrolites/codegen/gen_khigh.py)

## 5. 为什么 `(ss|ss)` 的求积根可能不用计算？

考虑四个未归一化 primitive s 高斯的普通库仑积分。忽略收缩系数时，结果为

$$
(ss|ss)=\frac{2\pi^{5/2}}{pq\sqrt{p+q}}
 e^{-ab|\mathbf A-\mathbf B|^2/p}
 e^{-cd|\mathbf C-\mathbf D|^2/q}F_0(T),
$$

其中 $F_0(T)=\int_0^1 e^{-Tt^2}\,dt$。归一化和收缩系数再由相应实现约定乘入。

Rys 求积通常生成求积根与权重，用它们计算角动量多项式及其递推。对于这个最简单的 s 类积分，没有额外角动量多项式需要在根处求值：被求积的多项式就是常数 1。单根求积的结果只需要对应权重，也就是这里的 $F_0(T)$。即使通用程序算出了根，随后乘到的多项式仍是 1，根没有进入最终结果。

这就是“有些中间量最终不参与结果”的具体含义：并不是删去一个很小但非零的物理贡献，而是避免构造后续没有使用的数据。`fastk_prologue.cu` 中的 `rys_weight0` 直接计算所需权重，`kbody0000` 使用它，不必先调用通用的根与权重生成流程。小 $T$、一般 $T$ 和大 $T$ 还需要不同数值处理，以避免公式在极限处不稳定。[源码](../../electrolites/kernels/fastk_prologue.cu)

高角动量的递推一般真正使用求积根，不能照搬这个删减。核导数会引入升阶项，`ssss` 的导数也不能仅凭原始角动量标签套用同一个推理。尺度分离积分还需要相应算子下的权重表达式；上式只解释普通库仑情形。
